Shadow IT grew up

2026-09-01 · 7 min read essay textmasks

Seventeen people in HR, each solving the same problem. Seventeen agents, each built independently, each with its own read on what "handle the onboarding request" means. Nobody told IT. Each one has API access. Each one touches production systems — the HRIS, the identity provider, the ticketing queue, whatever was closest at hand when someone needed the thing to actually work. Ask what the org's attack surface looks like and the honest answer is: nobody knows, not because it's hidden, but because nobody counted. The seventeen weren't built in secret. They were built in the open, one at a time, each one reasonable on its own, and the sum was never anybody's job to add up.

This is the shape of the problem worth naming precisely, because the name people reach for — shadow IT — undersells it.

A different order of magnitude

Shadow IT used to mean a marketing team paying for a SaaS tool on a personal card because procurement took three weeks. It was a governance headache. Someone eventually found the subscription on an expense report, brought it into the fold or shut it down, and the risk, while real, had a ceiling. A rogue spreadsheet tool doesn't act. It sits there, holding data, waiting for a human to do something with it.

An agent doesn't wait. It has permissions and it uses them. It reads files, writes to systems, calls APIs, and does all of this on a loop, without someone approving each step. The difference between the old shadow IT and the new one isn't really about how many unauthorized tools exist — organizations have always had more of those than IT could see. The difference is in what the tools are now capable of doing once they exist. A forgotten subscription is a line item. A forgotten agent is a standing, autonomous actor with a key to something.

The organizational trap underneath the technical one

Here's the part that makes this hard to fix, and it's not a tooling problem — it's an incentive problem. Building an agent to handle one HR person's version of the onboarding workflow takes about twenty minutes. It solves their problem today. Coordinating seventeen people around a shared, reviewed, governed primitive instead takes weeks, meetings, and — critically — asks each person to give up a piece of local autonomy for the sake of a system-wide property that they, personally, will barely feel.

That's a bad trade from where any one of the seventeen is standing. The cost of coordination is immediate and personal — the meetings, the compromise, the loss of "my agent does exactly what I want." The benefit of coordination is distributed and delayed — a smaller attack surface, an auditable set of permissions, a system nobody has to reverse-engineer six months from now. Rational individual behavior, aggregated, produces an irrational organizational outcome. This is why the fix can't just be "tell people to stop." The twenty-minute agent will always win that argument in the moment it's built.

What a shared primitive actually looks like

The concrete answer isn't a policy memo. It's giving the seventeen a version of the twenty-minute agent that's already coordinated — a shared, versionable, auditable persona definition that multiple teams can reference instead of each hand-rolling their own. This is the textmasks idea: define the agent's scope, permissions, and behavior once, in a form that can be reviewed, diffed, and improved centrally, and let teams build on top of that shared definition instead of starting from a blank prompt each time. Seventeen bespoke agents become one persona, referenced seventeen times, each instantiation inheriting the same guardrails by construction.

It's worth being honest about where this breaks, though, because it does break, and pretending otherwise would undercut the whole argument. A persona defined in personas/ can encode a structural denial — this agent cannot touch that system, full stop, enforced by the shape of the definition itself. But agents don't run in personas/. They run in whatever native format the target platform expects, and getting there requires rendering the persona into that format's agents/ directory. Somewhere in that render step, the structural denial — the thing that was actually enforced, not just requested — becomes advisory prose. A hard boundary becomes a strongly worded instruction. The agent's runtime doesn't know the difference between "cannot" and "please don't." Only the definition did, and the definition doesn't run.

Where the boundary actually is

This is the same tension that keeps showing up across these posts, in different clothes each time. You can write the rule with total precision. You can define least-privilege by construction, at the level of the definition. But enforcement has an edge, and past that edge, the system is trusting something instead of guaranteeing it. The PR is the last honest moment before code ships; after that, you're trusting the code did what the review thought it would. The persona is the last honest moment before an agent runs; after that, you're trusting the render preserved what the definition enforced.

The question isn't whether that boundary exists — it always does, somewhere. The question is whether you know exactly where it is, or whether you're finding out the way the seventeen HR agents found out: after the fact, when someone finally counts.
